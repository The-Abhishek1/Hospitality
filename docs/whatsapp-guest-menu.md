# Live WhatsApp guest menu

Owners open **WhatsApp Automation → Guest menu & links**. Configure the greeting, categories and template-backed services, then save with automatic replies enabled. Up to 30 categories and 100 services are supported, with automatic paging inside each WhatsApp message. A connected number is required for live delivery. Saving a disabled menu prepares configuration without activating automatic replies. Test by sending a **new** Hi or MENU to that hotel's connected number. New guest messages and manual rich replies wake the cloud worker, throttled to one wake per five seconds. The existing minute cron is the fallback. Nothing backfills old greetings.

Guests receive a real WhatsApp interactive list. Selecting an item sends a CTA link, a photo gallery, a private guest page or a reception handoff acknowledgment. Supported greetings include Hi, Hello, Hey and MENU; commands are case insensitive and tolerate trailing punctuation. After a delivered menu, numbers 1–10 also select the corresponding current option. Repeated greetings within 30 seconds are suppressed. Other incoming text remains for staff; this is a deterministic menu, not a general AI chatbot.

Hotel options include stay details, documents, food, services, check-in/checkout requests, directions, photos, review, website and reception. Up to ten may be enabled. These guest-page actions open the corresponding PWA screen; they never independently check a guest in/out, charge a payment or place an order.

## Public and private content

- Directions, review, website and hotel photos are public. Use valid public HTTPS destinations. Saving updates the shared hotel link settings used by review automations and offline drafts.
- Upload JPEG, PNG or static WebP hotel photos up to 4 MB through the administrator-only endpoint, or paste public image links. Up to five photos can be configured. Each is sent as an image message with an optional caption. External images must satisfy Meta's media requirements. Uploads are public hotel assets: never upload guest IDs or private photos. The server checks staff permission, origin, size and image signatures, generates the storage filename, and keeps the service-role credential server-side. Public gallery storage grants no client write policy. Removing a photo from the menu stops future sharing; it does not delete an already uploaded public object or recall messages already sent.
- Private stay pages require the existing staff-verified guest authorization, conversation binding, matching current phone and exactly one eligible reservation at this hotel. Unknown contacts and ambiguous bookings receive verification guidance. Phone matching alone is insufficient.
- A private page uses the server-configured guest portal origin and a fresh random reservation token, valid for seven days, under `/s/<token>`. No staff-app URL or generic portal homepage is substituted. Navigation uses PWA `view` and `intent` parameters. The browser cannot supply a portal origin. The worker records the trusted origin for manually requested Inbox guest links too.

## Owner and staff replies

The Inbox now offers **Share hotel information** shortcuts for the configured menu, private page actions, directions, photos, reviews and website. These are explicit staff replies and remain available while the automatic menu is paused. All rich replies require an open conversation, an active connection, no contact opt-out and an open 24-hour reply window. The Inbox previews outgoing option lists, images and CTA links with normal delivery status. Incoming option selections show their label rather than only `[interactive]`.

Selecting reception switches on human handoff and queues one acknowledgment. Automatic menu, photo and link replies then remain silent until staff explicitly resumes automation through the existing conversation controls. STOP/UNSUBSCRIBE retain the existing opt-out behavior. START/SUBSCRIBE retain the existing opt-in behavior; a start message does not establish private guest identity or marketing consent.

## Queue and deployment

Migration 82 adds per-hotel menu configuration, a durable inbound-intent queue, rich outgoing snapshots, public hotel photo storage, Inbox shortcuts and previews, and `claim_outbound_messages_v5`. Previous consumers cannot claim rich replies. The updated cloud and Node workers expand menu intents and deliver the validated rich payload through the existing claim/acknowledgment pipeline. Provider timeouts and unknown outcomes are never blindly retried.

Window expiry, opt-out, connection/sender changes, configuration revision, guest authorization, reservation eligibility and automatic handoff state are checked again before delivery. Configuration changes invalidate queued old-menu snapshots. Enabling a menu does not replay messages received while disabled. Each provider message and generated reply is deduplicated. A setting change cannot recall a provider request already in flight.

This feature implements interactive **service-window replies**. Scheduled/event notifications still use the approved body-only template transport. Image headers/buttons in proactive templates and arbitrary conversational AI remain separate work; the offline draft designer does not activate those capabilities.

## Editable categories and template-backed services (migration 83)

The current menu editor supports up to 30 owner-defined categories and 100 services. Owners can rename, reorder, move between categories, enable or remove services. Root/category menus show seven business rows per page, with Previous, More and Main menu rows added within WhatsApp's ten-row limit. Provider IDs include the published configuration version; old selections return the current menu rather than selecting a changed service.

Every enabled service in a published grouped menu requires an approved, supported and recently synchronized template from this hotel's current WABA. Templates can be reused. Choose **Create a new template for this service** to open a prefilled template name in another tab; review, explicitly submit to Meta, then sync in the original menu tab and assign it. Unfinished menus can be saved with automatic replies disabled. Existing flat menus remain operational until their owner explicitly saves the grouped configuration; viewing the editor changes nothing.

Template creation now offers a static text header or JPEG/PNG image header, a static footer and up to two static HTTPS link buttons. Images uploaded through the property-scoped photo endpoint are sent to Meta's Resumable Upload API as template samples and registered as that template's delivery image. Imported image-header templates need an owner-uploaded delivery image in the template library before assignment. The browser cannot supply arbitrary fetch targets to the server. Dynamic public URL buttons are unsupported; private stay links use the runtime `{{portal_url}}` body field. Scheduled event automation transport remains body-only, separately gated from rich service-template support.

Service templates can use named guest/hotel/stay fields. Templates with event-specific payment, order or invoice parameters and positional fields are not eligible for generic menu replies because a menu selection cannot reliably identify that context. Any guest-specific field requires the existing verified conversation/guest binding and exactly one eligible reservation. Unverified guests get verification guidance instead of template personal data. The template selected for a private-page action must include `{{portal_url}}`, which opens the relevant PWA screen. A service selection does not directly confirm airport pickup, check-in, checkout or another operational request; the guest completes the corresponding portal form or reception handles it.

Configuration, template approval/fingerprint/freshness, sender, reply window, opt-out, handoff, private authorization and template-image changes are checked before delivery. Header/footer/static button content is approved by Meta; the queue snapshots the selected template and named body/image components. All actual Meta template submissions remain explicit owner actions. Rich-template creation, paging and delivery are covered by grouped-menu behavior tests, transport tests, isolated API tests and `034_whatsapp_grouped_templates.test.sql`.

## Shared hotel information and media (migration 85)

Property settings → Hotel information owns the public Maps, review and website destinations, plus the reusable hotel media library. Guest menu now edits only the welcome message, categories, services and assigned templates. Menu saves preserve the canonical hotel links, including when an older draft is still open. Existing flat menus keep working until an owner saves their grouped menu.

Template creation can copy a shared destination into message text or a static link button, and select an owned JPEG/PNG from the photo library. A copied URL stays part of that template; later hotel settings changes do not rewrite it. The `{{review_url}}` body field continues to resolve the hotel's current shared review destination. Photo headers and buttons remain guest-service template features; hotel-event templates use text and an optional footer.

New uploads create property-scoped photo metadata only after storage succeeds. Existing menu and template photo references are retained in the library. Removing a library entry archives its metadata while preserving the public object and existing template delivery image. Cross-hotel access and unvalidated client metadata writes are denied. Hotel-link changes are version-checked and appear in property settings history; neither resource changes nor template creation activate sending.

Validation: `036_hotel_message_resources.test.sql` covers isolation, stale-menu protection, template preservation and independent settings versions. `npm run test:hotel-information --prefix apps/web` covers button snapshots, photo ownership, upload authorization, content detection, failed-registration cleanup and archival without file deletion.
